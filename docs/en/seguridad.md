# Security

MyDGX's security model: what it protects, how, and what the person who
administers it must configure.

## Network exposure

- The dashboard (`8088`), the gateway (`4000`) and the profile runtimes listen
  only on `127.0.0.1` by default.
- The recommended remote access is an **SSH tunnel** (opened by the menu bar
  app or `ssh -L`). Alternative: an HTTPS proxy with authentication.
- If `HOST` is a network address, MyDGX requires `MYDGX_DASHBOARD_PASSWORD` or
  `MYDGX_API_KEY`. If `GATEWAY_HOST` listens on the network, it requires `GATEWAY_API_KEY`.
  Without protection, the dashboard responds `503` and the gateway does not start.

## Authentication

| Surface | Mechanism |
|---|---|
| Dashboard interface | If `MYDGX_DASHBOARD_PASSWORD` is set, login with a signed `HttpOnly`, `SameSite=Strict` cookie with an absolute expiry of 60 minutes. If the deployment generates it, the menu bar app's "Copy dashboard password" only works until the first successful login (marker `data/.dashboard-password-claimed`). |
| Dashboard API | The web cookie above, or the `X-MyDGX-Key: YOUR_API_KEY` header for scripts when `MYDGX_API_KEY` is set. |
| Gateway | `Authorization: Bearer YOUR_GATEWAY_API_KEY` or `x-api-key` for clients that are not on loopback. |
| Open WebUI tools | Their own key, `OPENWEBUI_TOOL_API_KEY`, generated by the deployment. |

Keys and passwords are compared in constant time (`hmac.compare_digest`).
Login limits failed attempts per client. Secrets are defined in the
DGX's `.env`, never in the code.

## Protection against other websites (CSRF and DNS rebinding)

Even if the API listens only on loopback, a page open in a browser on the
same machine or over the tunnel could try to call it. Dashboard and gateway apply:

1. **`Host` validation.** Only loopback, the listening address (or
   the machine's IPs and name if it listens on all of them) and `TRUSTED_HOSTS` are accepted. An
   external domain that resolves to `127.0.0.1` (DNS rebinding) gets `403`.
2. **Origin validation** on `POST`, `PUT`, `PATCH` and `DELETE`. An
   `Origin` other than the service's own or an allowed one (`GATEWAY_CORS_ORIGINS`, and the
   Vite development server) is rejected, as is any `Sec-Fetch-Site: cross-site`.
   Clients that are not browsers (curl, SDK, Open WebUI) do not send
   `Origin` and are not affected.

Each rejection is recorded in the logs as `http.cross_site_blocked`.

## Confirmations and privileged operations

- Deleting models or profiles requires typing the exact name.
- Stopping services, engines or memory mode requires a confirmation text
  (`stop comfyui`, `liberar memoria`...).
- Updating or repairing the system requires `ENABLE_SYSTEM_UPDATES=true` and
  `ACTUALIZAR MYDGX` or `REPARAR MYDGX`. Controlling services requires
  `ENABLE_SERVICE_CONTROL=true`. Installing firmware requires
  `ENABLE_FIRMWARE_UPDATES=true` and `ACTUALIZAR FIRMWARE`. All are disabled
  by default. They can be turned on from Settings, but only by typing
  `ACTIVAR ACTUALIZACIONES`, `ACTIVAR FIRMWARE` or `ACTIVAR SERVICIOS`; the
  change is audited and posts a notification.
- `/etc/sudoers.d/mydgx` grants only a closed list: the APT update
  commands, the repair script, `systemctl` on the MyDGX services,
  shutdown, and the clock-cap program with the fixed arguments `apply`
  and `clear` only. **Never** `NOPASSWD: ALL`. The browser cannot send
  arbitrary commands. The clock cap also requires the confirmation phrase
  `APLICAR LIMITE GB10` or `QUITAR LIMITE GB10` after the Settings dialog.
- The assistant only **proposes** actions. They run when the user
  confirms them and expire after `ASSISTANT_ACTION_TTL_SECONDS`.
- Every action is recorded in the audit (`GET /api/audit`).

## Profile apps

An app only runs if it meets all of these conditions:

- it is a direct subdirectory of `PROFILE_APPS_ROOT` and is not a symbolic
  link;
- it belongs to the MyDGX user and its `start.sh` is not writable by group or
  by others;
- it is in the `PROFILE_APPS` list, if that list has been defined.

It is launched with a minimal environment, without `HF_TOKEN` or MyDGX keys, and its output goes
to `logs/apps/`. If it is cancelled or exceeds the maximum time, its entire process
group is stopped.

## Secrets and logs

- `HF_TOKEN` and the keys exist only in the server's `.env`. They are not returned
  to the browser (the API only indicates whether they are configured), they are not stored in
  SQLite and they are not written to logs.
- Logs redact authorization headers, cookies, tokens and sensitive
  fields before persisting. Example: `Authorization: Bearer ***REDACTED***`.
- The deployment **does not copy** `.env`, `.env.*`, `*.env`, `*.pem`, `*.key`, `.git`
  or `.cursor` to the DGX. Only the `*.env.example` templates are copied.

## Deployment and supply chain

- **DGX SSH key.** The first connection shows the fingerprint and asks for
  confirmation (`--interactive`). The fingerprint is stored in `~/.MyDGX/known_hosts`
  (`MYDGX_KNOWN_HOSTS`). In non-interactive mode, an unknown or
  changed key aborts the deployment, unless it matches
  `MYDGX_SSH_HOST_FINGERPRINT=SHA256:...`. `MYDGX_SSH_ACCEPT_NEW=1` accepts
  new keys, never changed ones, and is only for ephemeral machines. The
  health check only replaces a changed key if it matches the expected
  fingerprint. The MyDGXTray setup wizard stores the fingerprint with
  `ssh-keyscan` before sending any password (trust on first use,
  with the fingerprint visible) and never replaces an existing fingerprint.
- **sudo password without Terminal.** `--sudo-password-stdin` reads one line from
  standard input, closes that input for the rest of the process and forwards the
  line only over the standard input of the final SSH. On the Spark, `sudo -A` reads it
  through a 0700 askpass from a 0600 file in `/dev/shm` (or `$TMPDIR`),
  which is deleted on completion or failure. It cannot be combined with `--interactive` and never goes
  through arguments, environment variables or logs.
- **Verified installers.** Ollama is checked by SHA-256 and a fixed version.
  Node.js comes from NodeSource's signed APT repository, with its key
  fingerprint verified. hashcat is checked by SHA-256. The native
  Claude Code installer requires `MYDGX_CLAUDE_INSTALLER_SHA256`.
- **Pinned versions.** Open WebUI by version, SearXNG by image digest,
  ComfyUI by commit and llama.cpp b12669 by verified commit.

## Multimodal services

- Whisper limits the upload size (`Content-Length` and *chunked* bodies).
- The TTS worker restarts automatically if it dies. Errors return
  the tail of its log, without request data.
- Personal reference voices are not uploaded to the DGX.

## Recommendations

- Keep dashboard and gateway on localhost and use the SSH tunnel.
- Set `MYDGX_DASHBOARD_PASSWORD`, `MYDGX_API_KEY` and `GATEWAY_API_KEY` to
  distinct random values, directly in the DGX's `.env`.
- Enable `ENABLE_SYSTEM_UPDATES`, `ENABLE_FIRMWARE_UPDATES` and
  `ENABLE_SERVICE_CONTROL` only when you are going to use them, and turn them off afterwards.
- Do not commit `.env`, databases, model caches or private
  keys to Git.
